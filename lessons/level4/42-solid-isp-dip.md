# Урок 42. SOLID · ISP и DIP

## Цель
Понять два финальных принципа SOLID: тонкие интерфейсы (ISP) и зависимость от абстракций (DIP).

## Словарик новых слов
- **ISP (Interface Segregation)** — клиент не должен зависеть от методов, которые не использует.
- **DIP (Dependency Inversion)** — полагайся на абстракции, а не на конкретные реализации.
- **Инъекция зависимостей (DI)** — передача зависимости извне (например, через конструктор).

## Теория «с нуля»

### ISP: аналогия с меню
Представь меню, где в каждом блюде все ингредиенты сразу. Тебе нужно только яйцо, но «блюдо» тянет всё остальное. Лучше отдельные блюда (отдельные интерфейсы) под конкретную нужду.

### Плохо: «жирный» интерфейс
```csharp
interface IWorker
{
    void Work();
    void Eat();
    void Sleep();
    void PrintReport();
}
```
Класс `Robot` должен реализовать и `Eat()`, и `Sleep()`, хотя не умеет. Это нарушение ISP.

### Хорошо: тонкие интерфейсы
```csharp
interface IWorker { void Work(); }
interface IReportable { void PrintReport(); }
```
`Robot` реализует только то, что нужно.

### DIP: аналогия — розетка и прибор
Прибор (класс) не должен сам себя подключать к конкретной розетке. Он «ожидает» питание извне. В коде: класс не создаёт свои зависимости внутри (`new`), а получает их через конструктор (инъекция).

### Плохо: new внутри
```csharp
class OrderService
{
    private readonly SqlOrderRepository _repo = new();   // жёсткая связь
}
```
Сменить хранилище сложно, тестировать без БД нельзя.

### Хорошо: инъекция через конструктор
```csharp
interface IOrderRepository { void Save(Order o); }

class OrderService
{
    private readonly IOrderRepository _repo;
    public OrderService(IOrderRepository repo) => _repo = repo;   // извне
}
```

Теперь можно подставить любую реализацию — и для тестов, и для смены БД. Зависимость направлена на абстракцию (интерфейс).

## Разбор типичных ошибок

| Ошибка | Что не так | Как правильно |
|---|---|---|
| Интерфейс с 15 методами | много лишнего для клиентов | дробить |
| `new` сервиса внутри другого сервиса | жёсткая связь | инъекция через конструктор |
| Глобальный `static`-сервис | скрытая зависимость | DI |
| Реализация «вхолостую» (throw) у ненужных методов | запах ISP | тoкие интерфейсы |

## Тест — проверь себя

**Вопрос 1.** Что означает ISP?
- A) Клиент не должен зависеть от ненужных ему методов.
- B) Интерфейсы должны быть сложными.
- C) Наследование запрещено.

✅ **Верно: A.**
Почему: тонкие интерфейсы под нужды клиента.
Почему неверны остальные:
- B — Наоборот, тонкие.
- C — ISP не про запрет наследования.

**Вопрос 2.** Что означает DIP?
- A) Зависеть от конкретных классов.
- B) Зависеть от абстракций (интерфейсов), а не от реализаций.
- C) Запретить абстракции.

✅ **Верно: B.**
Почему: полагаемся на контракты.
Почему неверны остальные:
- A — Это противоположность DIP.
- C — Абстракции как раз нужны.

**Вопрос 3.** Почему `new SqlOrderRepository()` внутри сервиса — плохо?
- A) Это быстро.
- B) Жёсткая связь: нельзя подменить для тестов и смены БД.
- C) Это не компилируется.

✅ **Верно: B.**
Почему: конкретная реализация прибита гвоздями.
Почему неверны остальные:
- A — Это не про скорость.
- C — Компилируется, но сцепление плохое.

**Вопрос 4.** Что такое инъекция зависимостей (DI)?
- A) Создание зависимостей внутри класса.
- B) Передача зависимостей извне (например, через конструктор).
- C) Удаление зависимостей.

✅ **Верно: B.**
Почему: DI — зависимость приходит снаружи.
Почему неверны остальные:
- A — Это противоположность DI.
- C — Это не удаление.

## Итог урока
- ISP: **тонкие интерфейсы под нужды клиента**.
- DIP: **зависимость от абстракций**, реализация приходит извне (DI).
- Инъекция через конструктор — основа тестируемости.
