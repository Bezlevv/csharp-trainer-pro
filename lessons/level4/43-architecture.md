# Урок 43. Архитектура и слои

## Цель
Понять, как организовывать большой проект: слои, направление зависимостей и структуру папок.

## Словарик новых слов
- **Архитектура** — «планировка» кода: как разделены части и как они связаны.
- **Слой** — логическая группа классов со своей ролью.
- **Domain (домен)** — бизнес-правила (ядро).
- **Infrastructure (инфраструктура)** — БД, внешние сервисы.
- **Зависимость** — ситуация, когда один класс использует другой.

## Теория «с нуля»

### Аналогия: планировка дома
Прежде чем строить дом, делают план: где кухня, где спальня, где коммуникации. Если строить хаотично — переделка одной комнаты рушит всё. Архитектура — план кода: каждому слою — своё место.

### Слои
Популярная схема (Clean Architecture, упрощённо):

```
Presentation (API/UI)  — ввод/вывод, контроллеры
        ↓
Application (сервисы)   — use cases, бизнес-сценарии
        ↓
Domain (сущности)       — правила, модели
        ↓
Infrastructure (БД)     — EF Core, файлы, внешние вызовы
```

### Главное правило: зависимости «внутрь»
- `Domain` **не знает** про `Infrastructure` (не использует EF Core).
- `Infrastructure` реализует интерфейсы, объявленные в `Domain`/`Application`.
- Это тот самый DIP из прошлого урока — теперь на уровне проекта.

### Пример структуры папок
```
src/Shop/
├── Domain/
│   ├── Entities/Product.cs
│   └── Interfaces/IProductRepository.cs
├── Application/
│   ├── Services/ProductService.cs
│   └── Dtos/ProductDto.cs
├── Infrastructure/
│   ├── Data/AppDbContext.cs
│   └── Repositories/EfProductRepository.cs
└── Presentation/
    └── Api/Program.cs
```

- Интерфейс репозитория лежит в `Domain` (или Application).
- Реализация — в `Infrastructure`.
- `Application` работает с интерфейсом, а не с EF.

### Зачем это нужно
- Смена БД не трогает домен/приложение.
- Лёгкое тестирование (подмена репозитория).
- Читаемость и предсказуемость.

## Разбор типичных ошибок

| Ошибка | Что не так | Как правильно |
|---|---|---|
| Domain использует DbContext | домен привязан к БД | убрать зависимость |
| Вся логика в Program | нет слоёв | разложить по слоям |
| Сервис создаёт репозиторий через new | сильная связь | DI через конструктор |
| Папки есть, но зависимости нарушены | формальность | следить за направлением |

## Тест — проверь себя

**Вопрос 1.** Какой слой — «ядро» с бизнес-правилами?
- A) Infrastructure
- B) Domain
- C) Presentation

✅ **Верно: B.**
Почему: Domain — сущности и правила.
Почему неверны остальные:
- A — Infrastructure — детали (БД).
- C — Presentation — ввод/вывод.

**Вопрос 2.** Куда направлены зависимости?
- A) От Domain к Infrastructure.
- B) К центру: к Domain (внутрь).
- C) В любую сторону.

✅ **Верно: B.**
Почему: внутренние слои не знают про внешние.
Почему неверны остальные:
- A — Это нарушение направления.
- C — Направление строгое.

**Вопрос 3.** Где обычно объявляется интерфейс репозитория?
- A) В Infrastructure.
- B) В Domain (или Application) — как контракт.
- C) В Presentation.

✅ **Верно: B.**
Почему: контракт принадлежит внутреннему слою.
Почему неверны остальные:
- A — Реализация — в Infrastructure, а контракт — внутри.
- C — Presentation — не место для контрактов данных.

**Вопрос 4.** Какая польза от слоёв?
- A) Код становится длиннее.
- B) Замена БД и тестирование упрощаются.
- C) Программа быстрее.

✅ **Верно: B.**
Почему: слои дают гибкость и тестируемость.
Почему неверны остальные:
- A — Не про длину.
- C — Не про скорость.

## Итог урока
- Архитектура — план, как разделить код.
- Слои: Presentation → Application → Domain ← Infrastructure (зависимости внутрь).
- Контракты — внутри, реализации — снаружи.
- Слои упрощают смену БД и тесты.
