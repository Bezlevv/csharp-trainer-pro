# Модуль 25: Микросервисы и очереди сообщений

> **Цель:** понять, что такое микросервисы, и как сервисы общаются через очереди (RabbitMQ/Kafka).

## Зачем это нужно
Крупные системы делят на микросервисы, а между ними общаются через **очереди сообщений**. Это позволяет не блокировать запросы и надёжно доставлять события. Тема уровня senior/архитектора.

## Теория

### 1. Монолит vs микросервисы
- **Монолит** — одно большое приложение, всё внутри.
- **Микросервисы** — набор маленьких независимых сервисов, каждый со своей ответственностью (заказы, оплата, уведомления).

Плюсы микросервисов: независимый деплой, масштабирование по частям, изоляция сбоев.
Минусы: сложность, сетевое взаимодействие, распределённые транзакции.

### 2. Как сервисы общаются
- **Синхронно** (HTTP/gRPC): запрос → ответ. Просто, но сервис ждёт.
- **Асинхронно** (очереди): сервис отправляет событие в очередь и не ждёт. Другие сервисы читают.

### 3. Очередь сообщений
Очередь — буфер между отправителем и получателем:
- отправитель (producer) публикует сообщение;
- очередь хранит его;
- получатель (consumer) читает.

Популярные: **RabbitMQ** (очереди, AMQP), **Apache Kafka** (логи событий, потоковая обработка).

### 4. Зачем очереди
- **Развязка**: сервисы не знают друг о друге напрямую.
- **Надёжность**: сообщение хранится, даже если получатель временно недоступен.
- **Балансировка нагрузки**: несколько получателей делят сообщения.
- **Масштабирование**: можно добавить обработчиков.

### 5. Событийный подход (Event-driven)
Сервис публикует **событие** (например, `OrderCreated`). Другие сервисы подписываются и реагируют. Это развитие паттерна Observer (урок 46) на уровне системы.

### 6. Пример: заказ в интернет-магазине
1. `OrderService` получает заказ.
2. Публикует событие `OrderCreated` в очередь.
3. `PaymentService` и `NotificationService` читают событие и делают своё.
4. Никто никого не ждёт синхронно.

### 7. Рекомендации
- Не злоупотребляй микросервисами: начинай с монолита, дроби по мере роста.
- События делай осмысленными (имя в прошедшем времени: `OrderCreated`).
- Обеспечь идемпотентность обработчиков (повторная обработка не должна ломать).

## Типичные ошибки

| Ошибка | Почему плохо | Как правильно |
|---|---|---|
| Микросервисы «ради моды» | сложность без выгоды | начинай с монолита |
| Синхронная цепочка вызовов | медленно, хрупко | событийный подход |
| Потеря сообщений без обработки ошибок | данные пропадают | повторные попытки/DEAD LETTER |
| Неконсистентные данные | распределённые транзакции сложны | событийная согласованность |
