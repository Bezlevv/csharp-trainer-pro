# Разбор кода — Модуль 00

> Формат: рабочий, но плохой код → находим проблемы → рефакторим.

## Пример 1: «Работает, и ладно»

### Исходный код

```csharp
Console.WriteLine("Введите число: ");
string input = Console.ReadLine() ?? "";
int number = int.Parse(input);
Console.WriteLine("Вы ввели число: " + number);
```

### Что не так

- Сложение строк через `+` (`"Вы ввели число: " + number`) — старый синтаксис. Читаемость хуже, легко ошибиться с пропущенным пробелом.
- `int.Parse` упадёт с исключением, если пользователь введёт текст, а не число.

### Как лучше

```csharp
Console.Write("Введите число: ");
string input = Console.ReadLine() ?? "";

if (int.TryParse(input, out int number))
{
    Console.WriteLine($"Вы ввели число: {number}");
}
else
{
    Console.WriteLine("Это не число!");
}
```

### Вывод

Используй интерполяцию `$""` вместo склейки через `+`, а для ввода от пользователя — `TryParse`, чтобы программа не падала.

## Пример 2: Копипаст без понимания

### Исходный код

```csharp
namespace MyNamespace
{
    class Program
    {
        static void Main(string[] args)
        {
            Console.WriteLine("Hello World");
        }
    }
}
```

### Что не так

- Это легальный код, но он написан по старому шаблону: понапрасну `namespace`, класс и `Main`. Кода больше, а смысла нет.
- Новичок, который копирует его не задумываясь, учится писать лишнее.

### Как лучше

```csharp
Console.WriteLine("Hello World");
```

### Вывод

Top-level statements — современный и предпочтительный способ. Но если встретишь старый формат в чужом проекте, не пугайся: внутри всё то же самое.

## Пример 3: «У меня работает в Visual Studio»

### Исходный код

Пользователь «всегда делал так» внутри Visual Studio и не проверял запуск из терминала. Проект отказывался собираться на другой машине: пропущен пакет, неправильная целевая версия .NET, закоммиченные `bin/` и `obj/`.

### Что не так

- Окружение одного человека не является стандартом для всех.
- Закоммиченные артефакты сборки (`bin/`, `obj/`) ломают репозиторий: каждый пересобирает мусор, появляются конфликты.

### Как лучше

- Всегда проверяй чистую сборку: `dotnet build` и `dotnet run` в терминале.
- Добавь `.gitignore` с `bin/`, `obj/`, `*.user` и другими артефактами IDE.

### Вывод

Твоё окружение — не эталон. Проверяй проект так, как его соберёт CI или другой разработчик: с нуля, из терминала.

## Пример 4: Hardcoded-строка с путём к файлу

### Исходный код

```csharp
string path = "C:\\Users\\ivan\\Documents\\save.txt";
Console.WriteLine($"Читаю файл: {path}");
```

### Что не так

- Путь зашит в код. На другой машине (или даже у того же юзера, но в другой папке) программа не найдёт файл.
- Обратные слэши `\\` легко сломать — а экранирование в строках иногда пропускают.

### Как лучше

```csharp
string path = Path.Combine(Environment.SpecialFolder.MyDocuments.ToString(), "save.txt");
Console.WriteLine($"Читаю файл: {path}");
```

### Вывод

Не зашивай жёстко пути и значения. Используй `Path.Combine` и переменные окружения — программа станет переносимой.

## Выводы по модулю

Главное в начале пути — не зубрить синтаксис, а понять, **что происходит** при сборке и запуске. Пиши маленькие программы руками, запускай их из терминала и исследуй, что появляется на диске. Это заложит фундамент для всей дальнейшей работы.
