# Модуль 13: Юнит-тестирование

> **Цель:** писать тесты, которые реально защищают от регрессий, и мыслить в стиле TDD.

## Зачем это нужно

Код, который нельзя разбить на проверяемые куски, накапливает долги: одна правка ломает другое. Тесты — «страховка» при рефакторинге, живая документация поведения и способ проектировать код, чтобы он был тестируемым. Средний разработчик пишет тесты, а не считает их роскошью.

## Теория

### 1. Зачем тесты

- Отлавливают регрессии (поломку старого при изменении нового).
- Документируют ожидаемое поведение.
- Упрощают рефакторинг — есть уверенность.

Базовый принцип — **пирамида тестов**: много быстрых юнит-тестов, меньше интеграционных, ещё меньше E2E.

### 2. TDD (кратко)

Красный → зелёный → рефакторинг:

1. Сначала пишем падающий тест (красный).
2. Пишем код, чтобы тест прошёл (зелёный).
3. Улучшаем код (рефакторинг), не ломая зелёный.

### 3. xUnit

Установка проекта тестов:

```bash
dotnet new xunit -n MyApp.Tests
dotnet add MyApp.Tests reference ../src/MyApp/MyApp.csproj
```

Базовые атрибуты:

- `[Fact]` — одиночный тест.
- `[Theory]` — набор сценариев с `[InlineData]`.

### 4. Утверждения `Assert`

| Метод | Что проверяет |
|---|---|
| `Assert.Equal(expected, actual)` | равенство |
| `Assert.NotEqual` | неравенство |
| `Assert.True` / `Assert.False` | истинность |
| `Assert.Null` / `Assert.NotNull` | null |
| `Assert.Throws<T>(() => ...)` | ожидаемое исключение |
| `Assert.ThrowsAny<T>` | любое исключение типа T |

### 5. AAA-паттерн

```csharp
[Fact]
public void Deposit_IncreasesBalance_ReturnsNewBalance()
{
    // Arrange — подготовка
    var account = new BankAccount();
    // Act — действие
    decimal result = account.Deposit(100);
    // Assert — проверка ожидания
    Assert.Equal(100m, result);
}
```

### 6. Именование

`Method_Scenario_Expected` — например, `Withdraw_InsufficientFunds_Throws`.

### 7. Моки

Моки подменяют внешние зависимости (БД, сеть, время). Чтобы мок был возможен — зависимость должна быть **интерфейсом** и вводиться через конструктор.

```csharp
public class OrderService
{
    private readonly IClock _clock;
    public OrderService(IClock clock) => _clock = clock;
    public bool IsExpired(Order order) => _clock.Now > order.Deadline;
}
```

С мок-библиотекой (Moq / NSubstitute) подменяем `IClock`. Можно и вручную — написать фейк-класс.

### 8. Что тестировать

- Бизнес-логику (расчёты, валидацию, переходы состояний).
- Граничные случаи.

Не нужно тестировать сам фреймворк (LINQ, Console, сериализацию).

## Типичные ошибки

| Ошибка | Почему плохо | Как правильно |
|---|---|---|
| Тест без утверждений | «делает вид» | `Assert.*` |
| Тест на `DateTime.Now` | хрупкий, недетерминированный | параметр/`IClock` |
| Один тест со множеством актов | трудно локализовать поломку | разбивать |
| Тест-дубликат | замедляет прогон | поддерживать уникальность |
| Покрытие ради процентов | формализм | покрывать важную логику |
