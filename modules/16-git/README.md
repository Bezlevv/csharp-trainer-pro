# Модуль 16: Git и рабочий процесс (бонус)

> **Цель:** уверенно работать с Git в терминале: история, ветки, слияния, pull request.

## Зачем это нужно

C# ты выучил, но в реальной команде код живёт в Git. Это система контроля версий: она хранит историю изменений, позволяет работать нескольким людям одновременно и откатываться к рабочему состоянию. GitHub/ GitLab — это «облачные» хостинги Git, где живут репозитории, ведётся код-ревью и крутится CI. Без Git не проходит ни один рабочий день разработчика.

## Теория

### 1. Основные понятия

| Термин | Значение |
|---|---|
| **Репозиторий** (`repo`) | папка с проектом + история изменений |
| **Коммит** (`commit`) | «снимок» состояния проекта в момент времени |
| **Ветка** (`branch`) | параллельная линия разработки |
| **Merge** | слияние веток |
| **Remote** | удалённый репозиторий (например, на GitHub) |

### 2. Базовый цикл

```bash
git init              # создать репозиторий
git status            # что изменилось
git add <file>        # проиндексировать изменения
git commit -m "сообщение"
git log --oneline     # история коммитов
```

**Рабочий процесс «изменить → закоммитить»:**

```bash
# 1. Изменил код
git status            # видно, что изменилось
git add src/Program.cs
git commit -m "fix: исправил вылет в меню"
```

### 3. Gitignore

Правило: не коммитить артефакты. Для .NET это `bin/`, `obj/`, `*.user`. Всё это уже есть в `.gitignore` курса.

### 4. Ветки

```bash
git branch feat/new-feature   # создать ветку
git checkout feat/new-feature # переключиться
git switch -c feat/new-feature # создать и переключиться сразу
```

**Основное правило:** `main` — всегда рабочая; новые фичи — в своих ветках, затем merge через pull request.

### 5. Merge и rebase

**Merge** — создаёт коммит слияния:

```bash
git checkout main
git merge feat/new-feature
```

**Rebase** — перекладывает твои коммиты на актуальную вершину:

```bash
git pull --rebase origin main
```

**Правило:** никогда не rebase запушенные чужие коммиты — история уже публична.

### 6. Откаты

```csharp
git revert <commit>   # отменить опубликованный коммит (безопасно)
git reset --soft HEAD~1  # отменить локальный коммит, сохранив изменения
git reset --hard HEAD~1  # отменить локальный коммит полностью
```

### 7. Conventional Commits

Типы коммитов: `feat`, `fix`, `refactor`, `test`, `docs`, `perf`, `build`, `ci`, `chore`.

```text
fix(api): return 404 when user missing
feat(ui): add dark theme
docs: add architecture diagram
```

### 8. GitHub: pull request

1. Создал ветку, закоммитил, запушил: `git push -u origin feat/...`.
2. На GitHub — «Compare & pull request».
3. В описании: что меняешь и зачем, как проверено.
4. Код-ревью → merge.

### 9. CI/CD

GitHub Actions выполняет проверки на каждый push/PR: сборка, линт, тесты. Если проверки не прошли — PR не мёржится. В этом курсе CI настроен в `.github/workflows/build.yml`.

## Типичные ошибки

| Ошибка | Почему плохо | Как правильно |
|---|---|---|
| Коммит `bin/`, `obj/` | артефакты в истории, конфликты | `.gitignore` |
| Коммит секретов | пароли навсегда в истории | никогда не коммитить `.env` |
| Огромные коммиты | сложно ревьюить и откатывать | маленькие логичные коммиты |
| `git reset --hard` на запушенном | теряется чужая работа | `git revert` |
| Сообщение «asdf» | через месяц непонятно | conventional commits |
