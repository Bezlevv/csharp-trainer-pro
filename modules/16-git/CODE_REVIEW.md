# Разбор кода — Модуль 16

> Формат: плохие практики Git → почему → как правильно.

## Пример 1: Коммит с `bin/` и `obj/`

### Плохо

```bash
git add -A
git commit -m "feat: done"
# в коммит попали bin/ и obj/
```

### Почему

- Артефакты сборки засоряют историю, создают конфликты и увеличивают размер репозитория.

### Как надо

```bash
# в .gitignore:
bin/
obj/
*.user
```

## Пример 2: Секреты в истории

### Плохо

```bash
git add .env
git commit -m "chore: add env"
```

### Почему

- Даже если потом удалить файл, секрет останется в истории навсегда. Ротация ключа не отменяет утечки.

### Как надо

- Никогда не коммитить `.env`, ключи, токены.
- Если уже закоммитил — немедленно отзови ключ и очисти историю.

## Пример 3: `git reset --hard` на запушенном

### Плохо

```bash
git reset --hard HEAD~3
git push --force
```

### Почему

- Переписывает публичную историю и удаляет работу других разработчиков.

### Как надо

```bash
git revert <sha>   # безопасный обратный коммит
```

## Пример 4: Сообщение коммита «asdf»

### Плохо

```bash
git commit -m "asdf"
```

### Почему

- Через месяц никто не поймёт, что менялось. `git bisect` и changelog бесполезны.

### Как надо

```bash
git commit -m "fix(auth): handle null token"
```

## Пример 5: Огромный коммит

### Плохо

```bash
git commit -m "big update"
# переделал весь проект одним коммитом
```

### Почему

- Сложно ревьюить, откатывать и связывать с задачами.

### Как надо

- Маленькие коммиты по одному логическому изменению.

## Пример 6: Пуш без проверок

### Плохо

```bash
git push  # не прогнал тесты и линт
```

### Почему

- Ломаешь CI, и коллеги получают сломанный код.

### Как надо

```bash
dotnet build && dotnet test
git push
```

## Вывод

Git — это дисциплина. Хорошая история коммитов и правильная работа с ветками делают проект понятным для команды и безопасным для откатов.
