# Модуль 19: Продвинутая архитектура

> **Цель:** проектировать приложения, которые легко расширять, тестировать и поддерживать на уровне больших проектов.

## Зачем это нужно

Когда проект растёт, «просто классы» перестают спасать. Нужна **архитектура** — правила, как раскладывать код по слоям, чтобы доменная логика не зависела от фреймворков и БД. Это и есть уровень senior: уметь видеть большую систему и принимать архитектурные решения.

## Теория

### 1. Слои и направления зависимостей

Классическая трёхслойная модель:

```
Presentation (UI/API) → Application (сервисы) → Infrastructure (БД, внешние сервисы)
```

Зависимости направлены **внутрь**, к домену. Домен — ядро, ни от чего не зависящее.

### 2. Clean Architecture

Популярная реализация идеи слоёв (по Роберту Мартину):

```
┌──────────────────────────────┐
│   Presentation (API/UI)      │  внешний слой
├──────────────────────────────┤
│   Application (сервисы,      │  use cases, команды
│   CQRS, медиаторы)          │
├──────────────────────────────┤
│   Domain (сущности,          │  бизнес-правила
│   value objects, интерфейсы) │
├──────────────────────────────┤
│   Infrastructure (БД, HTTP,  │  детали: EF Core, HttpClient
│   почта)                    │
└──────────────────────────────┘
```

**Ключевое правило:** зависимости направлены к центру. `Domain` не знает про `Infrastructure`. Интерфейсы объявляются в `Application`/`Domain`, а реализуются в `Infrastructure` (DIP).

### 3. Паттерн Repository

Одна из реализаций DIP для данных:

```csharp
// объявлен в Application
public interface IOrderRepository
{
    Task<Order?> GetByIdAsync(Guid id);
}

// реализован в Infrastructure
public sealed class EfOrderRepository : IOrderRepository
{
    private readonly AppDbContext _db;
    public async Task<Order?> GetByIdAsync(Guid id) =>
        await _db.Orders.FirstOrDefaultAsync(o => o.Id == id);
}
```

### 4. CQRS (кратко)

**CQRS** — разделение чтения и записи: `Command` (изменения) и `Query` (чтение) — разные модели. Упрощает масштабирование и оптимизацию чтения.

### 5. MediatR (упоминание)

Паттерн Mediator — команды распространяются через медиатор, а не через прямые ссылки. Популярен с CQRS.

### 6. Подход: сначала контракты

Проектируй API и интерфейсы до реализации. Контракты — «скелет» системы.

## Типичные ошибки

| Ошибка | Почему плохо | Как правильно |
|---|---|---|
| Домен знает про EF Core | смена БД ломает домен | DIP, интерфейсы в домене |
| Всё в `Infrastructure` | логика теряется | Application для use cases |
| Гигантский слой сервисов | отсутствие границ | разбивать по функционалу |
| Нет интерфейсов на границах | нельзя подменить для тестов | контракты |
